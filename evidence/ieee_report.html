Abstract

This paper presents the design, implementation, and evaluation of a four-node private-LAN web infrastructure built entirely on commodity MacBooks connected through a shared iPhone hotspot. The system delivers HTTPS-encrypted, load-balanced application traffic to private hostnames resolved by a custom dnsmasq DNS server, with end-to-end TLS authenticated by a self-signed Certificate Authority. Phase 2 of the project extends the baseline with four resilience and security mechanisms: backup DNS with automatic failover, DNS-TTL-driven edge migration (standby nginx), nginx upstream health-check failover across two Python Flask backends, and pf-based zero-trust backend isolation. Live demonstrations confirm that every single point of failure identified in Phase 1 has been addressed. Results show sub-second DNS failover, 30-second maximum edge-cutover delay (bounded by TTL), zero-error backend failover via nginx health checks, and effective LAN-layer backend isolation. All artefacts—configurations, certificates, evidence screenshots, and Wireshark captures—are publicly available in the team's GitHub repository.

Index Terms—DNS, dnsmasq, nginx, reverse proxy, TLS, load balancing, high availability, firewall, pf, DNS TTL, backend failover, private LAN.

I. Introduction

Modern web services rely on a layered stack—DNS resolution, TLS termination, reverse proxying, and backend compute—where each layer is a potential single point of failure. This project reproduces that stack at laboratory scale using four Apple MacBooks on a shared private LAN and demonstrates progressive resilience hardening across two evaluation phases.

Phase 1 established the core infrastructure: a private .test domain resolved by dnsmasq, a self-signed CA trusted on all client machines, an nginx HTTPS edge on port 8443, and two Python Flask backends load-balanced in round-robin. Phase 2 adds backup DNS, a standby edge with DNS-cutover, nginx upstream health checking, pf packet-filter isolation of backend ports, and a structured troubleshooting playbook.

The remainder of the paper is organised as follows. Section II describes the system architecture. Section III details the Phase 2 extensions and their experimental results. Section IV presents the troubleshooting methodology. Section V maps the lab components to real cloud equivalents. Section VI concludes with lessons learned.

D. TLS Certificate Chain

A 4096-bit RSA root CA was generated on Mac 2. The server certificate is a 2048-bit RSA leaf signed by the CA with Subject Alternative Names DNS:app.Kuch_Nahi.test and DNS:api.Kuch_Nahi.test, plus extendedKeyUsage=serverAuth. The CA was added to the macOS System Keychain on all four Macs via security add-trusted-cert, enabling /usr/bin/curl to verify the certificate without -k.

III. Phase 2 Extensions and Results

A. Backup DNS (Extension A)

Objective. Eliminate the DNS layer as a single point of failure.

Implementation. An identical dnsmasq instance was deployed on Mac 4 (10.7.15.153:53) with the same A-records as the primary. All Macs were configured with two DNS resolver addresses: 

sudo networksetup -setdnsservers "Wi-Fi" \
  10.7.6.152 10.7.15.153

Experiment. Ayush issued dig app.Kuch_Nahi.test (confirmed SERVER: 10.7.6.152), then Hardik stopped dnsmasq. Without any client reconfiguration, macOS's resolver automatically retried via the second entry.

Result. The subsequent dig returned SERVER: 10.7.15.153 with the correct answer 10.7.31.75. The website remained available throughout. Failover latency was imperceptible (<2 s timeout before retry).

Key insight. A DNS failure (SERVFAIL / timeout) differs fundamentally from a backend failure (502 Bad Gateway): DNS failure prevents TCP from opening; backend failure manifests only at Layer 7 after a successful TCP+TLS session.

B. TTL and DNS Cutover (Extension B & E)

Objective. Migrate all client traffic from the primary nginx edge (Mac 2) to the standby edge (Mac 3) using only a DNS record change, and demonstrate TTL-driven cache expiry in real time.

Implementation. Kabir deployed nginx on Mac 3 with the same upstream pool, identical TLS certificates (AirDropped from Mac 2), and X-Edge: standby-mac3 response header. Hardik's dnsmasq TTL was set to 30 seconds.

Experiment. Ayush ran a continuous ping loop against app.Kuch_Nahi.test. Hardik changed the dnsmasq A-record from 10.7.31.75 to 10.7.11.100. Hardik's own curl immediately returned X-Edge: standby-mac3 (no cached answer), while Ayush's loop continued resolving 10.7.31.75 for approximately 30 seconds before switching.

Cache flush demo. After restoring the original record, Ayush flushed her OS resolver cache (dscacheutil -flushcache; killall -HUP mDNSResponder); the loop switched IP immediately without waiting for TTL.

Result. Two clients simultaneously resolved the same hostname to different IPs, directly visualising TTL cache staleness. Edge cutover completed within one TTL window (≤30 s). This confirms DNS-based blue-green deployment semantics at LAN scale.

C. Backend Failover (Extension D)

Objective. Demonstrate automatic, transparent failover when one backend becomes unavailable.

Implementation. The nginx upstream block was updated with health parameters: 

upstream backend {
  server 10.7.11.100:3001
    max_fails=1 fail_timeout=10s;
  server 10.7.15.153:3002
    max_fails=1 fail_timeout=10s;
}

Experiment. Ayush ran a 6-request loop through the HTTPS edge, confirming alternating X-Backend: A / B headers. Kabir then terminated Backend A. The loop was re-run immediately.

Result. Every response in the post-failure loop returned X-Backend: B with HTTP 200; zero 5xx errors were observed. After Kabir restarted Backend A and approximately 10 seconds elapsed, alternation resumed automatically. This confirms that proxy_next_upstream retried the failed connection on the surviving upstream within the same request cycle.

D. Firewall Backend Isolation (Extension C)

Objective. Enforce zero-trust network segmentation so that backend ports (3001, 3002) are reachable only from the authorised nginx edge (10.7.31.75).

Implementation. Kabir and Ayush applied pf rules on Mac 3 and Mac 4 respectively: 

# Mac 3 — protects port 3001
pass in quick on lo0 all
pass in quick proto tcp \
  from 10.7.31.75 to any port 3001
block in quick proto tcp \
  from any to any port 3001

An analogous ruleset was applied on Mac 4 for port 3002.

Experiment. Before enabling pf, Hardik (Mac 1) curled both backends directly—both returned 200 OK. After enabling pf, Hardik's curls timed out after 5 s (curl: (28) Connection timed out). Abuzar (Mac 2) curled both backends—both returned 200 OK (whitelisted). Hardik then curled via HTTPS edge—200 OK, confirming end-users are unaffected.

Result. LAN-level zero-trust backend isolation was successfully demonstrated. The pattern is equivalent to AWS Security Groups restricting inbound traffic to the Application Load Balancer's security group only.

VI. Discussion

A. Remaining Single Point of Failure

The primary nginx edge (Mac 2 / 10.7.31.75) remains the single point of failure. The standby edge (Mac 3) is live and tested, but cutover is manual—requiring Hardik to edit the dnsmasq A-record. Automated health-check-driven DNS failover (e.g., Route 53 health checks) would remove this dependency and reduce mean-time-to-recovery from ~30 s (manual + TTL) to near-zero.

B. TTL Implications for Real Deployments

The 30-second TTL was chosen for demonstration speed. Production systems typically use 300–3600 s, requiring TTL to be lowered 24–48 hours before a planned migration. Our experiment directly visualised this trade-off: longer TTLs reduce DNS server load but increase client staleness during cutover.

C. TLS Without a Public CA

The self-signed CA approach is functionally equivalent to an internal enterprise CA. The extendedKeyUsage=serverAuth extension and proper SAN entries ensured that macOS and /usr/bin/curl validated the certificate correctly via the System Keychain. Homebrew's curl, which uses its own CA bundle, required the explicit --cacert flag—a subtle but important difference exposed during troubleshooting.

VII. Conclusion

This paper demonstrated that production-grade resilience patterns—backup DNS, DNS-TTL-driven edge migration, upstream health-check failover, and zero-trust backend isolation—can be reproduced and evaluated at laboratory scale with commodity hardware and open-source software. Each Phase 2 extension addressed a specific single point of failure identified in Phase 1 and was validated with live, reproducible demonstrations.

The most significant observation is that failures at different OSI layers produce fundamentally different symptoms and require different diagnostic tools. A structured layer-by-layer methodology proved essential for rapid fault isolation. These principles scale directly to cloud environments, where the same patterns manifest as Route 53 failover routing, ALB health checks, and Security Group isolation.

VIII. Viva Q&A

Q1: Why did dig show the new IP while ping showed the old one?

dig sends a fresh UDP query to the DNS server, bypassing the OS resolver cache. ping resolves through the OS cache, which retains the old answer until the TTL (30 s) elapses. This is why the ping loop was used to visualise cache expiry in real time.

Q2: DNS failure vs. backend failure?

DNS failure: name does not resolve; TCP cannot open. Backend failure: DNS resolves, TCP connects to nginx on 8443, but nginx cannot reach the backend and returns 502 Bad Gateway. The network layer is healthy; the application layer is broken.

Q3: Single point of failure and its mitigation?

The nginx HTTPS edge on Mac 2. Mitigation: standby nginx on Mac 3 (10.7.11.100) with DNS cutover. With TTL=30 s, full failover completes within 30 seconds of the dnsmasq A-record change.

Q4: Where does TCP end and TLS begin?

TCP ends after the 3-way handshake (SYN → SYN-ACK → ACK). TLS begins immediately after with ClientHello. In Wireshark: tcp.flags.syn==1 shows the handshake; tls.handshake shows ClientHello, ServerHello, and Certificate. Application data (GET /api/status) is sent only after the TLS Finished exchange.
